交互详解 · 一段代码怎么跑起来（可切换语言）

一段代码怎么跑起来

宏观上所有语言同一条路；差别在「各自怎么处理」。关键一问：这个进程到底是谁——是程序本身，还是一台虚拟机（JVM / CPython / V8）把程序代码当数据加载进来跑？点标签切语言。

唯一对所有语言都成立的：CPU 永远只执行机器码。区别是这段机器码是程序本身（AOT），还是解释器 / VM + JIT 的产物（字节码语言）——源码本身可能从不变成机器码（纯解释）。
尾链里 基础库（glibc / libstdc++）是可选的一层封装：静态链接、或 Go 这类运行时可绕过 libc 直发系统调用；但系统调用这道用户态↔内核态的门谁都绕不过，再往下才是内核与 CPU/ISA。

原理详解

上面讲每种语言各自怎么跑；下面四块是它们共用的底层机器——点标签切换。

核心机制 · 解释器怎么跑一段字节码（Python / Java / JS 通用）

解释器本身是个原生程序，核心是一个 switch 分派循环

字节码语言的「VM」说白了就是一个普通的原生程序（它的机器码在进程的 .text）。它的心脏是一个循环：取一条字节码 → switch 跳到这条 opcode 的处理逻辑——源码里是一段 C 函数，但构建解释器时就已经 AOT 编成机器码、躺在 .text 里 → CPU 执行这段现成机器码 → 取下一条。字节码只是被它读取的数据。

// 解释器的心脏（简化）
for (;;) {
  op = *pc++;            // 取下一条字节码
  switch (op) {
    case LOAD:  push(local); break;
    case ADD:   push(pop()+pop()); break;
    case CALL:  call_func(); break;
    // …每条 opcode 对应一段处理代码（构建解释器时已编成机器码）
  }
}
  • 字节码 = 数据：每条 opcode 查 switch 跳到它的处理代码。这些代码用 C 写，但构建 CPython 时就已 AOT 编成机器码——运行期 CPU 跑的是这份现成机器码，解释器不为程序代码生成任何新机器码。
  • 纯解释（CPython）：到此为止，每次都走这个循环。慢，但简单、可移植。
  • 解释 + JIT（Java/JS）：解释器顺便数每段代码跑了多少次；热点被 JIT 编成真机器码缓存起来，下次绕过 dispatch 循环直接执行。
  • Java 的分层：解释器(L0) → C1(轻量 JIT，快编、顺便采集热度) → C2(重度优化 JIT)。C1/C2 都是 JIT，解释的是解释器。

实线＝冷 / 解释路径（字节码被解释器逐条解释、解释器本身也在 CPU 上跑）；虚线＝热代码路径（数到热点 → 触发 JIT → 以字节码为输入编成机器码 → 这段热机器码直接在 CPU 上跑）。

⚠ 两条路最终都由 CPU 执行机器码——CPU 只会跑机器码；区别是它跑的是「解释器」还是「程序自身的专用机器码」

① 解释执行时，CPU 在跑什么

CPU 跑的是解释器自己的机器码。对每一条字节码，都重复一遍：
取码 → switch 查跳转 → 执行该 opcode 的处理机器码（C 写的、构建时编好）→ 回循环顶 ↺
一条字节码 ≈ 几十条 CPU 指令的间接开销，还没法跨字节码优化。

② JIT 后，CPU 在跑什么

热点字节码被一次性编成程序自身逻辑的机器码。之后 CPU：
连续直跑这段机器码：无取码 / 无 switch / 无回环
还能跨指令优化（值留寄存器、内联、删冗余检查）——就是普通原生机器码。
⚡ 所以 JIT 快：解释＝「CPU 跑一个通用解释器去逐条翻译字节码」，每条都付分派开销；JIT＝「CPU 直接跑这段逻辑的专用机器码」，编一次、之后零分派——同样的活常快 10～100×。代价是编译要花时间，所以只对热点才值得。
Java 细节 · HotSpot 内部：字节码解释器 + C1 / C2 分层编译

一个方法怎么从「解释」逐步升到「重度优化的机器码」

HotSpot 里有三套执行引擎：一个字节码解释器负责解释，两个 JIT（C1、C2）负责编译。方法越热，待遇越高；所有编译产物都进 Code Cache。

L0 解释字节码解释器
逐条 switch 解释执行，同时统计调用次数 / 循环回边次数（数热度）。刚启动的代码都在这跑。
↓ 热度过阈值（温）
C1 · L1–3Client 编译器（轻量 JIT）
编译快、优化保守，并插桩采集 profile。先让程序快起来，同时摸清谁是真热点。→ 机器码进 Code Cache。
↓ profile 显示是真热点（烫）
C2 · L4Server 编译器（重度优化 JIT）
基于 profile 做内联 / 逃逸分析 / 循环优化，生成最快的机器码。→ 机器码进 Code Cache。
Code Cache独立的本地内存区（不是 Java 堆）。C1/C2 编出的机器码都放这里；下次调用直接跑机器码，绕过解释循环。
deopt（去优化）＝ 赌错了就退回：JIT 的激进优化都基于乐观假设（赌某情况永远成立，于是省掉检查、生成极快的机器码）。假设被打破时，这份机器码就是错的，HotSpot/V8 便丢弃它、退回解释器重新正确执行，之后可再编译——这是「乐观优化」能成立的安全网。
// V8 的例子
add(1,2); add(3,4);　→ 赌「a,b 一直是整数」，编出跳过类型检查的快机器码
add("x","y");　　　→ 假设破！guard 发现是字符串 → deopt 退回解释器，按拼接重算 "xy"
常被赌的假设：类型/对象形状稳定、调用点单态（→内联）、某分支从不走；Java 还有「没有子类覆盖此方法」(CHA)，后来加载了覆盖的子类 → deopt。
V8（JS/Node）同理，只是分更多档：Ignition（解释器）→ Sparkplug（基线 JIT）→ Maglev → TurboFan（重度优化）。思路一致：先解释、数热度、热点逐级 JIT、假设破了就 deopt 退回解释器。
共用机器 ① · 编译器 = 前端 → IR → 后端

所有编译器都是这三段，换的只是实现

前端只管读懂源语言，后端只管生成某个 CPU 的指令，中间靠 IR（中间表示） 解耦。字节码语言的 javac 也是编译器——只是它的"后端"停在字节码，真正的 codegen 推迟到运行期的 JIT。

共用机器 ② · 链接器 = 把碎片拼成能跑的整体

编译只产出一堆目标文件，链接器才拼成可执行

每个源文件单独编成目标文件 .o（含「我用了 printf 但不知道它在哪」的未决符号）。链接器把这些符号和库里的实现对上、合并成一个整体。

静态链接（编译期拼死）

  • 库代码（.a）直接拷进可执行文件
  • 自包含、换机器能跑；但大，每个程序各带一份
  • 默认：Go、Rust（rlib）、musl 静态构建

动态链接（运行期再拼）

  • 只记「我要 libc.so」，代码留在共享库（.so/.dll）
  • 多进程共享、可单独升级；但要环境里有那个库
  • 默认：C/C++ 链 libc、系统共享库
VM 语言里，运行时自己（java/python/node）就是被这样链接出来的原生可执行文件——字节码/源码是它启动后再加载的数据，是另一回事。
机器码跑起来 · 经典 x86 地址翻译（两进程案例）

两个进程、相同的虚拟地址，怎么落到不同的物理内存

机器码里写的是虚拟地址。经典 x86 保护模式走完整三段：逻辑地址 →(分段)→ 线性地址 →(分页)→ 物理地址。让两个进程用相同的虚拟地址，看它们各自落到不同物理页帧。

进程 A（浏览器）
mov eax, [0x08048000]
读虚拟地址 0x08048000
进程 B（编辑器）
mov eax, [0x08048000]
读虚拟地址 0x08048000
↑ 两个进程用的是同一个虚拟地址，彼此却互不干扰——秘密全在下面的翻译链
① 逻辑地址段选择子 : 偏移
CPU 拿到的是 段选择子:偏移（如 CS:0x08048000），段选择子指向描述符表某一项。
↓
② 分段GDT / LDT
段选择子查 GDT（全局，全系统共享）或 LDT（每进程一份）→ 取段基址。线性地址=段基址+偏移。现代 64 位平坦模型段基址=0，这步近乎透明。
↓
③ 线性地址= 段基址 + 偏移
分段的产物。平坦模式下≈那个虚拟地址本身，交给分页硬件（MMU）。
↓
④ 分页CR3 → 页目录 → 页表
这步才是两进程分道扬镳的地方。每个进程有自己一套页表，根在 CR3。切进程时 OS 换 CR3，同一线性地址查到不同物理页帧：
进程 A 的 CR3 → A 的页表 → 物理页帧 0x200000
进程 B 的 CR3 → B 的页表 → 物理页帧 0x5A0000

同一虚拟地址 0x08048000，进程 A 落物理 0x200000、进程 B 落 0x5A0000——地址空间隔离就这么来的。
为什么一个进程读不到另一个进程的数据？ 每个进程都有一整套属于自己的虚拟地址空间（0 → 最高地址），它「以为整台机器的内存都归它」，根本不知道别的进程存在。它手里只有虚拟地址，而翻译用的页表（CR3 指向的那套）只登记了它自己的页——进程 A 想碰进程 B 的数据，它的地址空间里压根没有通往那些物理页的映射，连个有效地址都写不出来。
所以进程隔离不是「禁止读」，而是压根够不着：访问没映射的地址 → 触发缺页 → 段错误（SIGSEGV）。内核和共享库是例外——它们被映射进每个进程（同一份物理页），所以人人可用。进程间要通信得走专门渠道（管道 / 共享内存 / socket），由内核牵线。
关键寄存器：CR0（开关保护/分页）、CR2（缺页时存出错的线性地址）、CR3（当前进程页表根=PDBR，切进程就换它）；CR1 保留。
现代简化：64 位长模式用平坦模型，段基址≈0、分段近乎关掉，实际只剩「虚拟≈线性 →(分页)→ 物理」。ARM 没有分段，只有分页（根在 TTBR0/1）。翻译结果由 TLB 缓存。
